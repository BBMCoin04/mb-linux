### 隔离回归的关键场景

- `sshd -T` 为 22、socket 实际监听 2222 且没有 `SSH_CONNECTION` 时，仍保留 2222。
- 其他进程监听端口不能通过 SSH 监听验证。
- IPv4 尾随点、越界值及 IPv6 非法结尾被拒绝；端口边界与协议得到校验。
- SSH 有效配置不符、实际监听不符、Fail2ban action 端口落后时，会请求恢复事务。
- 只有有效配置、监听及动作端口都通过，才进入确认保留流程。
- socket 模式重启 SSH 主进程以接收新套接字；非 `KillMode=process` 的服务拒绝自动重启。
- Fail2ban 多个动作名称正确解析；只保护 UDP 的动作不算 SSH TCP 防护。
- 同步端口保留自定义失败阈值和封禁时长。
- 明确关闭 sshd jail；后加载配置再次启用时，检测冲突并恢复管理文件。
- 首次创建 jail 不尝试重启不存在的 jail；重启失败导致 jail 消失时重新载入原配置。
- 白名单失败会恢复原文件，支持 IP / 网段规范化并拒绝 `/0`。
- 定时任务创建失败不改 SSH；快照先于写入建立。
- 确认、过期、正在恢复、恢复失败等状态有不同处理；未确认会进入恢复路径。
- 恢复程序还原 SSH / Fail2ban / UFW 文件及端口清单；服务命令失败或 UFW 状态无法读取时不会报告成功。
- 本地完整安装包含恢复程序和快捷命令；第二个文件替换失败时成套回退。
- 版本不一致、降级、快捷命令被占用、不可信源码目录得到拒绝。
- 安装器复用父进程操作锁，避免更新自锁；低版本远程安装器在执行前被拒绝。
- 菜单在 EOF 时退出；指定 DNS 不可达时，系统旧缓存不能掩盖直接查询失败。

模拟系统命令只写临时记录，不执行真实 apt、systemctl、UFW、iptables、nft、Swap 或 Docker 操作。恢复程序的权限门槛仅在测试驱动中替换；生产入口仍要求 root。测试不需要 sudo。

### 真实 Fail2ban 解析场景

两个版本各执行同一组 8 项检查：

1. 启用 sshd 并使用 systemd backend。
2. 自定义次数、统计窗口和封禁时长被正确解析。
3. jail 的端口与 TCP 协议进入实际 action 参数。
4. `enabled = false` 覆盖发行版 `.conf` 中的启用值。
5. 更晚的 `.local` 可以再次覆盖这个值，证明需要合并配置核验。
6. 白名单新增地址保留全局既有地址。
7. 没有全局白名单时，自动切换到独立列表，配置仍能通过。
8. 手工 action 端口可以不跟随 jail 的 `port`，证明只检查管理文件不够。

Fail2ban 0.11.2 的上游归档包含 Python 2 语法。测试前执行了上游 `fail2ban-2to3`，并把临时副本的 `from collections import MutableMapping` 改为 `from collections.abc import MutableMapping`，使其可在测试环境的 Python 3.11 上运行。未修改其配置解析逻辑。它不是对 Ubuntu 某个打补丁发行包的直接验收，也没有把第三方源码放入交付包。

## 尚未完成的实机验证

当前环境没有可用的 root Ubuntu 测试机，也没有运行 Docker / Podman 虚拟测试机。因此，没有执行真实 VPS 的系统软件安装、SSH 重载、UFW 规则修改、Fail2ban 日志消费、真实封禁、远程断线重连或重启验收。

隔离测试验证逻辑、输入输出和恢复分支；真实解析测试验证配置兼容性。它们不能证明所有云镜像、内核、网络后端或发行版都已实测。

`.github/workflows/check.yml` 是已提供的检查配置；并未代用户上传或执行 GitHub Actions。其 Ubuntu runner 上仍是隔离回归，不是服务器网络实测。

## 建议的实机验收

在可使用云平台网页控制台的临时 Ubuntu VPS 上：

1. 完整安装并确认 `lm version` 为 1.5.0。
2. 准备并放行一个测试 SSH 端口；新端口登录成功后确认保留。
3. 再做一次端口修改但不确认，确认原端口能重新登录且配置恢复。
4. 为测试网站添加端口后切换 UFW 收紧，分别测试确认与不确认两条流程。
5. 启用 Fail2ban、添加测试可信 IP、调整规则、关闭防护，并核对实际状态。
6. 从另一台受控测试主机验证 SSH 失败登录和封禁 / 解封；不要拿唯一管理出口进行封禁测试。
7. 在确认或撤销所有待处理事务后，再测试重启后的服务状态。
